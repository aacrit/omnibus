# 2026-11-22: T4, `render_episode` is the new generic driver; `render_week33` is not literally removed (builder, from show bible v2 section i/r ticket 4)

Section i's line reads "`render.py` gains a generic `render_episode(rundown)` and loses `render_week33()`." The acceptance line that actually binds is stronger: "Issue 33's frozen v1 path stays intact." The two pull against each other if read literally - `render_week33` is the whole of that frozen path's drawing code (test cards, the framings board, day bars, the v1 lower thirds, count cards, the clock, credits, end board, the title macro), tied to `episodes/33/rundown.json`, `data/week-33.json` and `episodes/33/echo-pick.json` directly, not to a screenplay. Deleting or folding it into `render_episode` to satisfy the sentence literally would be a rewrite of the frozen path this ticket has no mandate to touch, and risks exactly the kind of drift the freeze exists to prevent.

So: `render_week33` keeps its name and its body, untouched. `render_episode(rundown, out_dir)` is the new, separate, generic entry point this ticket actually builds. The CLI's `mode` argument is generalised from the literal choice `"week33"` to a `week(\d+)` pattern (`render.WEEK_RE`): `week33` still calls `render_week33` exactly as before; `week<N>` for any other N calls `render_episode` on `episodes/<n>/screenplay.json` (or, with `--fixture`, `fixtures.EPISODE_V2_FIXTURE`). `episode-draft.yml`'s existing `python -m studio.graphics.render "week$ISSUE"` invocation needs no change to keep working for issue 33, and now also works for any v2 issue.

`render_episode` itself only draws the four subtypes this ticket adds (`render.V2_RENDERERS`: `bumper`, `locator`, `sot_super`, `brief_strip`). Every other v2 subtype section i keeps (`clock`, `count`, `lower_third`'s speaker/slate variants, `page`, `credits`, `end_board`) needs the rundown/2 normaliser's own data shapes (ticket 2) to drive sensibly; `render_episode` raises `NotImplementedError`, naming the subtype, rather than silently skipping one a future screenplay names. `graphics_shots(rundown)` - the pure walk of a screenplay's `parts[].shots`/`parts[].text` for graphic entries - is written generically enough that wiring in the next subtype is adding one function to `V2_RENDERERS`, not touching the walker.
